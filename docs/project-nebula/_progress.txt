## Architecture decision
- Local Windows crawler remains the only compute/data-production node; no crawler runs on the server.
- Reuse the encrypted-source multi-endpoint pattern only for the small signed `current.json` control plane.
- Do not distribute the full movie/series bundle through six raced endpoints.
- Use Cloudflare R2 + `media.magnetgoogo.com` as the primary immutable object store.
- Use existing Aliyun Nginx as the required China mirror; migrate the same publisher interface to OSS/CDN later if traffic grows.
- GitHub Raw/jsDelivr/CF Pages/Worker carry only current pointers and manifests as fallbacks.
- Worker must not proxy covers, details or resource objects; its free daily request quota would become the first bottleneck.
- Split payloads into channel cards, media details, resource sets and content-addressed covers.
- App fetches the highest signed `pointer_revision`, compares SHA-256 hashes and downloads only changed objects.
- Keep bundled seed + encrypted 72h disk cache + stale-while-revalidate network sync.
- Publish immutable objects first and update `current.json` last; rollback publishes a newer pointer revision to an older release.
- Sign pointer/manifest with Ed25519; optionally encrypt only magnet resource shards, not metadata/covers.
- Current full bundle is about 8.70 MiB; split loading can reduce first resource-page traffic to about 1 MiB.
- Existing control-plane naming drift (`mg-data` vs `maggoogo-sources`) is a pre-implementation blocker.

## Evidence
- Current movie bundle: about 2.23 MiB; series bundle: about 6.48 MiB.
- Current encrypted source payload: about 40 KiB, proving the two workloads need different data-plane designs.
- Official 2026 R2 limits reviewed: 10 GB free storage, 10 million free Class B reads/month, free egress.
- Official Workers free limit reviewed: 100,000 requests/day.
