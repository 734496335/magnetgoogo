# Project Nebula 开发规划

文档版本：V0.1
更新时间：2026-04-16

> 说明：本文件与 `ARCHITECTURE.md` 的契约字段与组件划分对齐。高风险或边界不清的能力不展开实现；对应模块仅列出占位任务与门禁条件。

## 1. 总体路线

里程碑路线按「低成本/高灵活 -> 无人值守/自动化 -> 体验打磨」推进：

1. 第一阶段：把 `sources.json` 作为唯一契约落地（可本地跑通）
2. 第二阶段：把 Web 客户端检索编排与流式渲染做成“可观测系统”
3. 第三阶段：把供给侧评分/标注形成闭环，并建立发布回滚
4. 第四阶段：商业化所需的权限/配额/强制更新链路抽象并接入到客户端
5. 第五阶段：安全治理、质量门禁、文档联动（DEV-LOG）工程化

## 2. 里程碑与交付物

### M0：工程骨架与契约工具链（1-2 天）

交付物：
- 定义并落地 `sources.json` 的 schema 校验（供给侧与客户端共享同一份 schema 定义）
- 建立 `RuleRegistry` 的 manifest 读取流程（客户端先用静态示例）
- Web 客户端页面骨架：搜索框、顶部状态栏、结果容器（空态）

验收标准（可测）：
- 本地启动时，客户端可以成功解析并加载示例 `sources.json`
- schema 校验失败能给出可定位的错误信息（字段路径 + 原因）

不进入编码的门禁：
- 待设计模块不做任何实现，只保持 `待设计`占位状态。

### M1：供给侧最小可用（MVP）数据管道（2-4 天）

交付物：
- DataFactory 的最小流水线：`bait_list` -> 探测样本 -> 解析元数据 -> 输出 `sources.json` v0
- scoring & tagging 的最小实现：提供 `score`、`tags`、`health` 的基本产出（指标来源先用可模拟数据）

验收标准：
- 对输入规则样本，能生成符合 schema 的 `sources.json`
- 生成产物包含 `generated_at`、`rulesets[].rules[].quality` 等必填字段

注意：
- 探测与评分可以先用“可替换的数据源适配层”（adapter 接口），便于后续扩展。

### M2：客户端并发检索与结果归一化（3-6 天）

交付物：
- `SearchOrchestrator`：并发请求队列、超时/重试、取消（`AbortController`）
- `SourceExecutor`：按 `request_template` 生成请求（普通 HTTP fetch）
- `ResultNormalizer`：统一结果结构并去重
- 结果流式渲染：先返回先显示，并更新全局状态栏

验收标准：
- 在可控延迟的模拟源上，首批结果渲染延迟达到预期（例如 < 1s）
- 搜索过程中取消可中断未完成请求且不发生内存泄漏（以浏览器性能面板或简单统计为准）

## M3：评分引擎闭环与发布回滚（4-7 天）

交付物：
- scoring & tagging 的指标实现：可靠性、时效性等
- 规则部署流水线：生成 `sources.json` 后进行抽样校验与健康统计
- 版本化发布与回滚：支持 `previous_good` 指针与客户端兼容策略

验收标准：
- 发布失败（schema 变更、质量门禁失败）能阻止上线并回滚
- `client_min_compatible_version` 被客户端正确识别（提示用户升级/禁用不可用规则）

### M4：商业与权限链路（3-5 天）

交付物：
- 客户端 `entitlements` 状态机与配额控制
- 服务端接口抽象（本地可用 mock）：`/entitlements/me`、`/usage/consume`、`/manifest`
- 免费/Pro 特权映射到 `ruleset_id`：
  - 免费：加载 `base`
  - Pro：额外加载 `pro_private`（或等价规则集）

验收标准：
- 免费配额耗尽后，客户端进入“限制状态”（不执行多余请求）
- Pro 解锁成功后，规则集切换无需刷新或可用最小刷新完成

## M5：安全治理与质量门禁（持续迭代，建议 1-3 天起步）

交付物：
- 文件类型识别与预览禁用策略（如 `.exe` 默认禁用预览）
- 结果字段安全渲染：HTML 转义、链接安全策略
- 日志与指标：记录请求成功率、失败原因聚合、首批结果耗时
- 文档联动：每次关键实现必须写入 `DEV-LOG.md`

验收标准：
- 常见 XSS 输入在页面渲染时被转义
- 故障场景下不会导致页面崩溃（错误边界 + 可观测日志）

## 3. 待设计模块门禁

以下模块在“架构/契约层”只占位，禁止在没有替代方案文档前进行任何编码：

1. `待设计：WAF/验证码穿透与交互接管机制`
2. `待设计：Cookie/User-Agent 劫持与持久化注入`
3. `待设计：应用商店“暗门”隐藏/规避关键功能`
4. `待设计：核心网络请求深度混淆实现细节`

门禁条件（必须满足其一）：
- 替代方案文档由你提供并明确可用输入/输出契约；
- 或由团队决定删除/替换对应能力（客户端降级也算替代方案）。

## 4. 与 `DEV-LOG.md` 的强绑定

当且仅当满足以下条件时，才能推进下一里程碑：
- 相关契约字段（尤其是 `sources.json` schema）有更新；
- 或引入了新的可观测指标/错误类型；
- 或“待设计模块”获得了新的替代定义。

每次满足上述任一条件，都必须在 `DEV-LOG.md` 追加记录，说明关键改动摘要与风险未决项。
