## 二、仍然存在的运行阻塞

### P0-1 当前电脑没有安装计划任务

实查结果：

```text
MagnetGoogo Movie Sources Safe Crawl = NOT_INSTALLED
```

所以目前只能判定“手动一键运行稳定”，不能判定“已经无人值守运行”。

### P0-2 计划任务不会唤醒睡眠电脑

当前任务模板：

```text
StartWhenAvailable = true
WakeToRun = false
```

错过的任务会在电脑恢复后补跑，但不会主动唤醒睡眠电脑。长期依赖个人电脑时，资源更新时间受开机、睡眠和网络状态影响。

### P0-3 更新结果不会自动到达已安装App

`magnetgoogo-app/src/core/resourceFeed.ts`只支持：

```text
ResourceFeedOrigin = bundled
```

电影、电视剧Feed和封面全部从APK Bundle读取。爬虫更新本地目录后，不会自动更新已安装用户的数据；必须重新预构建、打包和发布APK。

`run-movies-safe.ps1`和`run-media-offline.ps1`只生成本地Bundle，没有自动发布manifest、远程Feed或APK。

### P0-4 线上SSL自动续期实际未运行

服务器实查：

```text
证书到期：2026-08-02 00:06:13 UTC
剩余：6天
certbot-renew.timer：enabled但inactive
Next trigger：n/a
```

若不修复，`cn.magnetgoogo.com`和国内APK主下载地址会在证书到期后失败。其他配置镜像仍可降级，但主下载链路不稳定。

### P1-1 单一来源故障会冻结新鲜度

- SixV电影和SixV电视剧共享同一品牌、模板和镜像基础设施；多个域名只能抵御单域名故障，不能抵御统一模板改版或共同后端故障。
- DYTT备用端点最终重定向到同一主站，不是独立内容源。
- Meijumi只有一个正式端点。
- 当前电影严格100依赖SixV主池；当前电视剧严格100高度依赖Meijumi。

系统会保留上一份完整目录，不会退化或写坏，但单一核心来源失败时可能无法继续生成“最新100”。

### P1-2 自动追赶速度有限

安全自动化每个来源每12小时最多处理2批、每批5条。若离线多日后一次变化超过10条，冻结快照需要多轮才能补齐；在补齐前不会切换到下一份新快照。该策略保护源站，但大规模积压时新鲜度恢复较慢。

### P1-3 缺少端到端健康告警

当前有日志、状态命令和质量报告，但没有对以下状态主动通知：

- 计划任务未运行；
- 某来源连续失败或长期未更新；
- 正式目录未能达到100+100；
- 证书即将到期；
- 磁盘、Swap或数据库异常；
- Bundle生成成功但未发布。

## 四、当前用户请求实际经过哪里

### 资源页

电影100、电视剧100及200张封面随APK内置。用户浏览资源页不请求服务器。

### 搜索

搜索请求由手机直接访问各资源站，不经过中心服务器。用户规模不会集中消耗现有2核2G服务器，但资源站自身可能因域名变化、共享运营商NAT或反爬产生可用性波动。

### 中心服务

主要请求为：

- 远程配置；
- 加密搜索源规则；
- 匿名分析事件；
- 用户反馈；
- 官网与APK下载。

所以免费容量主要由Cloudflare Worker和R2额度决定，而不是服务器CPU。

### 当前App每次启动的中心请求

`configChecker.ts`和`secureSourceStore.ts`分别同时竞速6个端点，且竞速成功后没有取消其余请求。两个列表中各包含两个Worker地址。

每次启动大致产生：

```text
配置Worker请求：1—2
源规则Worker请求：1—2
分析事件Worker请求：至少1，搜索和复制操作可能继续增加
合计：轻度约3次，典型约5—10次Worker请求/DAU/天
```

分析事件每个批次写一个永久R2对象。典型使用大约产生2.5—5次R2 Class A写入/DAU/天。

### DAU估算

公式：

```text
可支持DAU = min(
  100,000 / 每DAU每日Worker请求数,
  1,000,000 / 30 / 每DAU每日R2写入数
)
```

| 使用模式 | Worker请求/DAU/天 | R2写入/DAU/天 | 免费理论上限 |
|---|---:|---:|---:|
| 轻度：1次启动、几乎不搜索 | 3 | 1 | 约33,000 DAU |
| 典型：1次启动、约2次搜索 | 5 | 2.5 | 约13,000 DAU |
| 活跃：2次启动、约4次搜索 | 10 | 5 | 约6,600 DAU |
| 重度：多次启动和操作 | 15 | 7 | 约4,700 DAU |

考虑以下非理想因素：

- 端点超时和回退；
- 未取消的并行竞速；
- 搜索、复制和打开事件多批次上报；
- 人工Dashboard读取；
- 机器人和恶意请求；
- 免费额度应保留至少30%—50%余量；

因此实际建议：

```text
保守稳定值：3,000—5,000 DAU
正常使用上限：约8,000—10,000 DAU
轻度使用理论值：13,000 DAU以上，但不应作为稳定承诺
```

按20%—30%的安装用户日活率，保守对应约20,000—50,000总安装用户。

当前约100 DAU只占保守容量的约2%—3%，短期完全没有服务器扩容压力。


主下载地址仍在阿里云Nginx。

| 新增下载 | 日流量 | 30天流量 |
|---:|---:|---:|

200Mbps峰值带宽约等于25MB/s，CPU不是APK分发瓶颈。真正不确定的是阿里云实例套餐包含的月流量；仓库和服务器无法给出该配额，因此不能把200Mbps直接解释为无限免费流量。

R2已有APK Bucket，使用R2自定义域名直接下载可利用免费公网流量，并避免阿里云月流量成为主要风险。

## 七、容量与稳定性代码风险

### 1. 启动请求被无谓放大

- 每次启动无条件后台同步，即使本地72小时缓存有效；
- 配置和源规则各自竞速6个端点；
- Promise.any成功后不取消失败或较慢端点；
- App发送`Cache-Control: no-cache`，Worker按该头跳过边缘缓存；
- Worker中的普通cache.put没有使用`await`或`ctx.waitUntil`。

这使当前免费容量至少被压缩2—4倍。

### 2. 分析接口可被滥用

`/api/events`公开写入R2，只按客户端提供的`did`做30秒Cache限流。攻击者可不断更换`did`绕过限制；`did`也没有严格长度和字符校验。

因此上述免费容量只适用于正常用户，不适用于恶意流量。攻击者可先耗尽100,000次Worker日请求或1,000,000次R2月写入。

### 3. R2分析对象永久保存

每个事件批次一个对象，无生命周期规则。用户规模增长后，Class A写次数通常先于10GB存储额度成为瓶颈；后台按对象逐个读取的Dashboard也会较早退化。

### 4. 服务器安全与运维风险

- 部署文档中保存了管理凭证明文，应立即轮换并从仓库历史移除；
- Admin端口对公网开放，应限制来源IP、VPN或仅内网访问；
- 证书续期timer失效；
- 服务器已使用Swap，不宜继续堆叠Node常驻服务。

## 八、推荐的下一阶段

按优先级：

1. 立即修复并验证证书续期，在2026-08-02前完成真实renew和Nginx reload。
2. 安装计划任务，增加`WakeToRun`，明确运行账户，并增加每日heartbeat告警。
3. 建立远程资源发布链：小manifest＋压缩Feed＋内容哈希封面，App保持内置Bundle兜底。
4. 将远程Feed和静态封面放到Cloudflare Pages或R2自定义域名，不经过动态Worker。
5. App本地缓存有效时不在每次启动同步；使用ETag或版本hash，竞速成功后取消其他请求。
6. 合并配置和源规则检查，删除旧Worker重复端点，停止发送无必要的`no-cache`。
7. 分析事件改为每会话或每日单批上报，增加IP＋设备双限流、字段校验和R2生命周期。
8. APK主下载迁移到R2直连域名，阿里云保留镜像。
9. 增加真正独立的电影和电视剧来源，使任何一个核心品牌失效时仍能形成100+100。
10. 轮换仓库中暴露的管理凭证，关闭或限制公网Admin端口。

完成第3—7项后，免费保守容量可提高到约20,000—30,000 DAU，且资源更新无需重复发布APK。
