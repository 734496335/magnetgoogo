# 影视资源本地爬取与静态分发架构——冻结契约

日期：2026-07-26
状态：ARCHITECTURE FROZEN / IMPLEMENTATION NOT STARTED
范围：影视资源本地爬取完成后的校验、发布、网络分发、App 增量获取、缓存、回滚和未来来源扩展

---

## 1. 结论

影视资源发布 **不应完整照搬现有加密源的 6 端点全量文件竞速模式**。

应采用“复用控制面、拆分数据面”的两层架构：

1. **控制面**：复用现有多端点能力，只发布和竞速获取几 KB 的签名指针文件 `current.json`；
2. **数据面**：电影、电视剧目录、详情、资源和封面使用独立静态对象存储，以不可变、内容寻址对象形式发布；
3. **主数据存储**：Cloudflare R2 + 自定义域名；
4. **国内镜像**：现有阿里云 Nginx，后续流量增大时平滑迁移到阿里云 OSS/CDN；
5. **GitHub / jsDelivr / CF Pages**：只承担小型指针和 Manifest 灾备，不承担高频封面和完整历史数据；
6. **Cloudflare Worker**：只做版本门控、端点选择和灾备，不代理全部静态数据请求；
7. **App**：内置种子数据，启动时先展示缓存或内置数据，再后台拉取 `current.json`，按哈希只下载变化对象。

核心原则：

> 本地电脑负责计算和爬取，云端只负责存储与静态分发；服务器不跑爬虫、不解析 Feed、不执行数据库查询。

## 2. 为什么不能直接照搬加密源

### 2.1 数据体量不同

当前实际数据规模：

| 内容 | Feed | 封面 | 总量 |
|---|---:|---:|---:|
| 电影 50 部 | 约 191 KiB | 约 2.04 MiB | 约 2.23 MiB |
| 电视剧 100 部 | 约 1.56 MiB | 约 4.88 MiB | 约 6.48 MiB |
| 合计 | 约 1.75 MiB | 约 6.92 MiB | 约 8.70 MiB |

现有加密源文件约 40 KiB。影视包已经是其两百倍以上，而且未来会持续增长。

如果每次更新都让所有用户下载完整 8.70 MiB：

- 1,000 次完整下载约 8.5 GiB；
- 10,000 次完整下载约 85 GiB；
- 100,000 次完整下载约 850 GiB。

因此必须把“列表、详情、资源、封面”拆开，并复用未变化对象。

### 2.2 更新频率不同

加密源通常以规则整体更新为单位；影视内容则可能每天只新增几部电影、更新几集电视剧或增加少量磁力。

完整覆盖发布会导致：

- 用户反复下载未变化的封面；
- 任何单集更新都会使整个电视剧 Feed 变化；
- Git 仓库历史快速膨胀；
- jsDelivr `@main` 缓存可能与最新状态存在时间差；
- 多端点全量文件难以保持原始传输字节完全一致。

### 2.3 访问模型不同

用户打开资源页时通常只需要：

1. 当前频道前几十条卡片；
2. 屏幕中可见的封面；
3. 点击某部影视后才需要详情和磁力资源。

不应该在进入资源页时下载全部影视的所有磁力。

## 3. 总体拓扑

```text
Windows 本地电脑
  └─ 一键运行本地爬虫
      ├─ SQLite / 快照 / 封面缓存
      ├─ 规范化与多源合并
      ├─ 数据质量门禁
      └─ Release Builder
          ├─ current.json（小型签名控制面）
          ├─ manifest.json（发布清单）
          ├─ channel indexes（频道列表分片）
          ├─ media details（影视详情对象）
          ├─ resource sets（磁力资源对象）
          └─ covers（内容寻址封面）
                    │
                    ├─ Cloudflare R2：主对象存储
                    ├─ 阿里云 Nginx/OSS：国内镜像
                    └─ GitHub/Pages/jsDelivr：仅 current + manifest 灾备

App
  ├─ 内置种子 Feed
  ├─ AES 加密磁盘缓存
  ├─ 多端点获取 current.json
  ├─ 验证 Ed25519 签名
  ├─ 比较对象 SHA-256
  ├─ 只下载变化频道/详情/资源
  └─ 网络失败时回退缓存或内置数据
```

本地电脑不对公网开放端口，也不作为用户请求服务器。

## 4. 控制面设计

### 4.0 现有发布链路必须先消除命名漂移

当前代码存在控制面仓库命名不一致：

- `AI-RULES.md` 与 `cf-gateway/wrangler.toml` 指向 `734496335/mg-data`；
- 本地 `admin.py` 和嵌套发布目录使用 `734496335/maggoogo-sources`；
- App 端静态 CDN 常量又使用 `mg-data`。

影视控制面实施前必须先确定唯一权威仓库和唯一权威域名，禁止让 Publisher 推送到一个仓库、Gateway 从另一个仓库读取。建议：

- 现有加密源继续由当前正式仓库承载，但先完成名称和地址收敛；
- 影视 `current.json` 以 R2 自定义域名为第一权威源；
- Git 仓库只作为控制面镜像，不作为影视数据事实源；
- 发布收据必须记录每个端点实际读取到的 `pointer_revision` 和 `release_id`。

### 4.1 `current.json`

`current.json` 是 App 每次检查更新时唯一必须请求的小文件。

建议结构：

```json
{
  "schema_version": "media-current/1",
  "pointer_revision": 108,
  "release_id": "20260726T231500Z-4c2f8b91",
  "manifest_path": "/v1/releases/20260726T231500Z-4c2f8b91/manifest.json",
  "published_at": "2026-07-26T23:15:00Z",
  "min_app_version": "0.2.1",
  "signature_key_id": "media-ed25519-2026-01",
  "signature": "..."
}
```

关键规则：

- `pointer_revision` 只增不减；
- 回滚时也发布一个更大的 `pointer_revision`，但可重新指向旧 `release_id`；
- App 比较多个端点返回值时，选择 **签名有效且 pointer_revision 最大** 的版本；
- 不使用纯 `Promise.any` 的“第一个响应即胜出”，防止最快端点恰好是旧缓存；
- 单端点可用时允许降级使用该端点；
- 指针必须签名，不能只信任 HTTPS 或 CDN。

### 4.2 控制面端点

建议保留现有六端点思想，但只同步小文件：

1. `media.magnetgoogo.com/v1/current.json`：R2 自定义域名，主端点；
2. `cn.magnetgoogo.com/media/v1/current.json`：阿里云国内镜像；
3. `magnetgoogo.com/media/v1/current.json`：CF Pages 静态镜像；
4. GitHub Raw：灾备；
5. jsDelivr：灾备；
6. `api.naoshiquan.com/media/current.json`：Gateway 灾备与版本门控。

Workers Dev 只作为开发或最后灾备，不作为国内主端点。

### 4.3 多端点获取算法

推荐使用“分阶段竞速 + 最高版本裁决”：

1. 立即请求 R2 自定义域名和阿里云镜像；
2. 300 ms 后仍未形成有效结果，再启动 Pages 和 Gateway；
3. 800 ms 后再启动 GitHub Raw 与 jsDelivr；
4. 在 1.5 秒裁决窗口内收集有效签名响应；
5. 选择 `pointer_revision` 最大者；
6. 记录成功端点，下次优先请求；
7. 所有端点失败时使用本地缓存或 APK 内置 Feed。

这比六端点同时请求更省电、省流，也比第一个响应胜出更能避免旧缓存。

## 5. 数据面设计

### 5.1 对象目录

建议统一使用：

```text
/v1/current.json
/v1/releases/<release_id>/manifest.json
/v1/objects/catalog/<sha256>.json
/v1/objects/detail/<sha256>.json
/v1/objects/resources/<sha256>.enc.json
/v1/covers/<sha256>.webp
```

对象路径由内容 SHA-256 决定。内容未变化时不重新上传，也不会产生新文件。

### 5.2 Manifest

```json
{
  "schema_version": "media-manifest/1",
  "release_id": "20260726T231500Z-4c2f8b91",
  "generated_at": "2026-07-26T23:10:00Z",
  "channels": {
    "movie": {
      "featured": {"hash": "...", "size": 18214},
      "latest_pages": [
        {"hash": "...", "size": 64231, "count": 50}
      ]
    },
    "series_us": {
      "updating": {"hash": "...", "size": 21340},
      "latest_pages": [
        {"hash": "...", "size": 57111, "count": 50}
      ]
    }
  },
  "details": {
    "media-id-1": {"hash": "...", "size": 2181},
    "media-id-2": {"hash": "...", "size": 1940}
  },
  "resources": {
    "media-id-1": {"hash": "...", "size": 15383, "encrypted": true}
  },
  "cover_base_path": "/v1/covers/",
  "counts": {
    "movie": 50,
    "series": 100,
    "resources": 1279,
    "covers": 150
  },
  "signature": "..."
}
```

Manifest 不应重复放完整影视详情和磁力，只保存逻辑对象到内容哈希的映射。

### 5.3 卡片、详情和资源分层

#### 卡片对象

仅保留资源页展示需要的数据：

- `media_id`
- 标题、年份、国家、类型
- 豆瓣/IMDb 评分
- 更新状态
- 画质标签
- 资源数量
- 封面哈希
- 详情对象哈希

不得携带完整剧情、导演演员和所有磁力。

#### 详情对象

点击详情后按需下载：

- 剧情简介
- 导演、演员
- 完整影片信息
- `resource_object_hash`

#### 资源对象

点击详情或查看资源时才下载：

- 磁力 URL
- 集数、季数
- 画质、字幕、版本信息
- info-hash

这样进入资源页时不会下载所有磁力。

### 5.4 分页与分片

- 每个频道建议每页 50 条；
- “精品推荐/追更速递”单独一个小对象；
- 最近更新按频道拆分；
- App 只下载当前频道首页；
- 用户下滑接近底部时再下载下一页；
- 新增来源不应形成新的 App Feed 文件，最终仍合并进现有频道。

## 6. 存储与端点角色

### 6.1 Cloudflare R2：主数据源

使用独立 bucket，例如：

```text
magnetgoogo-media
```

绑定：

```text
media.magnetgoogo.com
```

选择 R2 的原因：

- 适合大量静态对象和内容寻址文件；
- 无需维护文件服务器；
- 支持 S3 兼容上传；
- 可绑定自定义域名和 Cloudflare Cache；
- 当前数据量远低于免费存储额度；
- 网络出站不按流量收费；
- 新来源和历史版本增长时不需要改服务器程序。

R2 必须使用自定义域名，不使用 `r2.dev` 作为生产地址。

### 6.2 阿里云：国内镜像

第一阶段继续使用现有阿里云服务器 Nginx 静态目录：

```text
/var/www/media/v1/
```

只提供静态文件，不运行 Node/Python API。

当国内流量明显增加时，将同一 Publisher 后端替换为阿里云 OSS/CDN，App 和 Release Builder 不需要改变协议。

### 6.3 GitHub / jsDelivr

只保存：

- `current.json`
- 当前和少量历史 `manifest.json`
- 可选的小型频道索引

不保存：

- 全量封面历史
- SQLite
- 每轮完整 Feed 备份
- 大量资源对象

原因：Git 历史不适合作为高频生成数据的对象存储；高频提交会造成仓库膨胀，分支最新地址还可能受 CDN 缓存影响。

### 6.4 Cloudflare Worker

Worker 只承担：

- App 版本门控；
- 返回当前端点优先级；
- `current.json` 灾备代理；
- 可选会员分层；
- 轻量请求统计。

Worker 不承担：

- 每张封面代理；
- 每个详情对象代理；
- 每个磁力对象代理；
- 在线 Feed 拼装；
- 在线数据库查询。

否则免费 Worker 请求额度会比对象存储更早成为瓶颈。

## 7. 缓存规则

### 7.1 HTTP 缓存

| 文件 | Cache-Control |
|---|---|
| `current.json` | `public, max-age=60, must-revalidate` |
| `manifest.json` | `public, max-age=300, stale-while-revalidate=86400` |
| 内容寻址 JSON | `public, max-age=31536000, immutable` |
| 内容寻址封面 | `public, max-age=31536000, immutable` |

JSON 可由 CDN/Nginx进行 gzip 传输，但 Manifest 中的 SHA-256 必须针对规范化、解压后的原始 JSON 字节计算，不能依赖不同端点的压缩字节完全一致。

### 7.2 App 缓存

App 使用三级缓存：

1. 内存缓存；
2. AES 加密磁盘缓存，遵守项目 72 小时强制过期规则；
3. APK 内置种子 Feed。

页面策略：

1. 立即显示内存或磁盘缓存；
2. 后台检查 `current.json`；
3. 新版本只更新变化对象；
4. 下载、验签、解析全部成功后再切换缓存指针；
5. 任一关键对象失败，继续使用旧版本，不展示半新半旧数据。

封面使用内容哈希路径，变化后自然形成新 URL；未变化封面永久复用。

## 8. 发布原子性

### 8.1 发布步骤

本地一键流程应为：

```text
crawl
  → normalize
  → merge
  → data-quality gates
  → build staging release
  → verify release
  → upload immutable objects
  → verify remote objects
  → upload manifest
  → verify manifest
  → update current.json LAST
  → write publish receipt
```

`current.json` 必须最后发布。

### 8.2 发布成功条件

至少同时满足：

- R2 所有新对象上传且校验成功；
- 阿里云国内镜像所有新对象上传且校验成功；
- Manifest 签名、对象数量和哈希通过；
- 两个主数据端点都能读取 Manifest；
- 控制面至少两个端点成功更新 `current.json`；
- 发布后端点抽样读取通过。

任何条件失败：

- 不切换 `current.json`；
- 用户继续使用上一版本；
- 本地保留 staging 和失败报告，支持重新发布；
- 不删除已上传的不可变对象。

### 8.3 回滚

回滚不覆盖历史文件，仅发布新的 `current.json`：

```json
{
  "pointer_revision": 109,
  "release_id": "previous-good-release",
  "rollback_from": "bad-release",
  "signature": "..."
}
```

App 按最大 `pointer_revision` 接受该回滚，不会因为 `release_id` 较旧而拒绝。

## 9. 完整性、安全和加密边界

### 9.1 必须使用数字签名

建议使用 Ed25519：

- 私钥仅保存在本地发布电脑；
- App 内置公钥；
- `current.json` 和 `manifest.json` 分别签名；
- Manifest 保存每个对象的 SHA-256；
- App 下载后先验哈希，再解析和写缓存。

数字签名用于解决真正的完整性和来源可信问题。

### 9.2 是否加密影视 Feed

不建议把所有公开元数据和封面都加密：

- 无法防止 App 用户最终读取；
- 会破坏 CDN 图片缓存和浏览器兼容；
- 增加 App CPU、内存和发布复杂度。

建议：

- 频道卡片、评分、剧情和封面：公开、压缩、签名；
- 磁力资源对象：可使用现有 App 密钥加密，作为降低批量抓取便利性的防护；
- 新实现优先采用带认证的 AES-256-GCM；
- 必须明确：客户端内置密钥只能防止随手爬取，不能提供真正保密。

### 9.3 凭证

- R2 S3 凭证只存本地环境变量或 Wrangler 凭证；
- 阿里云继续使用 SSH Key；
- App 中不包含上传凭证；
- 发布日志不得打印 Secret；
- 私钥和对象存储凭证不得提交 Git。

## 10. 数据质量发布门禁

本地爬虫成功不等于允许发布。必须在发布前执行：

1. Schema 校验；
2. 电影、电视剧目标数量门禁；
3. Feed 不能比上个版本异常缩减；
4. `media_id` 唯一；
5. info-hash/URL 去重；
6. 季集顺序正确；
7. 跨季资源为 0；
8. 通用标题无法恢复数量不得增加；
9. 封面存在率达到阈值；
10. 类型、国家字段无 HTML 残片；
11. 所有 Manifest 引用对象真实存在；
12. 新版本首次加载估算体积不能异常膨胀。

推荐退化门禁：

- 频道数量下降超过 20%：阻断；
- 资源总数下降超过 30%：阻断；
- 封面完整率下降：阻断；
- 未知季集资源增加：阻断；
- 单对象超过预设上限：阻断并要求重新分片。

特殊业务变更需要通过显式 `--allow-regression <reason>`，并写入发布记录，不能静默绕过。

## 11. 爬虫扩展性

### 11.1 分层职责

```text
Source Adapter
  → Raw Observation
  → Normalizer
  → Canonical SQLite
  → Deduplicator / Merger
  → App Exporter
  → Release Builder
  → Publisher Backends
```

新增来源只增加 Adapter 和来源配置，不得直接生成一套新的 App 页面协议。

### 11.2 规范化数据库是唯一事实源

SQLite 中应保留：

- 原始来源观测；
- 标准影视实体；
- 来源到标准实体映射；
- 标准资源；
- 来源、解析和更新时间；
- 封面内容哈希；
- 发布版本关联。

App Feed 是数据库导出的消费视图，不是爬虫的主存储。

### 11.3 来源与 App 解耦

App 只认识：

- `movie`
- `series`
- 国家地区频道
- 类型
- 评分
- 更新状态
- 详情
- 资源

App 不应认识 6V、DYTT、Meijumi 等来源品牌。

来源变化、镜像失效或新站接入，不应要求发 App 新版本。

### 11.4 Publisher 接口

建议定义统一发布后端：

```text
PublisherBackend
  - head(path, hash)
  - upload(path, bytes, metadata)
  - verify(path, hash, size)
  - promote_current(pointer)
  - healthcheck()
```

实现：

- `R2Publisher`
- `AliNginxPublisher`
- `GitManifestPublisher`
- 后续 `AliOssPublisher`

Release Builder 不应包含 R2、SSH 或 GitHub 的具体命令。

## 12. App 加载状态机

```text
BOOT
  ├─ bundled seed available → render
  ├─ disk cache valid → render cache instead
  └─ background sync
       ├─ fetch signed current pointers
       ├─ choose highest pointer_revision
       ├─ same release → DONE
       ├─ fetch/verify manifest
       ├─ download changed current-channel objects
       ├─ atomically commit cache
       └─ refresh UI without full remount
```

详情页：

```text
open media
  ├─ detail cached → render
  ├─ fetch detail object
  ├─ resource list only fetched when needed
  └─ failure → retain metadata and show retry for resources
```

App 同一时间只允许一个 Feed 同步任务；页面卸载或切换频道时必须支持 Abort；列表对象更新应尽量保持 `media_id` 和 React 对象身份稳定，防止卡片闪烁。

## 13. 成本与容量判断

基于当前约 8.70 MiB 的完整影视数据：

- 使用内容寻址后，未变化的约 6.92 MiB 封面不会重复上传；
- 即使保留 30 个发布版本，实际存储也远小于简单复制 30 份完整包；
- 当前数据量距离 R2 免费 10 GB 存储额度很远；
- R2 当前提供每月 10 million 次免费 Class B 读取，且网络出站免费；
- 自定义域名配合边缘缓存后，大部分热门封面和索引不会反复命中 R2；
- 当前规模下，免费存储不是主要瓶颈；
- 如果所有数据请求都经过 Worker，Worker 免费版每日 100,000 请求会更早成为瓶颈，因此静态对象必须直接走 R2/阿里云。

第一屏成本估算：

- 当前平均封面约 40–50 KiB；
- 20 张可见/预加载封面约 0.8–1.0 MiB；
- 精简频道卡片索引约几十 KiB；
- 首次进入资源页可控制在约 1 MiB，而不是下载完整 8.70 MiB。

按 1 MiB 首屏估算：

- 1,000 个首次用户约 1 GiB；
- 10,000 个首次用户约 10 GiB；
- 后续只下载新增对象，通常远低于首次流量。

这些是产品容量估算，不是云厂商账单承诺；实施前和每次扩容前需重新核对官方额度。

## 14. 一键本地命令目标

最终用户侧只需要运行：

```bat
deploy\resource-index\run-and-publish.bat
```

建议支持：

```text
-Source all
-Refresh
-NoPublish
-DryRun
-Resume
-VerifyOnly
-PublishOnly
-Rollback <release_id>
-MaxBatches <N>
```

标准行为：

1. 没有参数：恢复未完成任务，完成后仅在数据有变化且全部门禁通过时发布；
2. `-Refresh`：获取新快照；
3. `-NoPublish`：只爬取和构建；
4. `-DryRun`：生成发布计划，不上传；
5. `-PublishOnly`：发布已验证 staging；
6. 任务退出码保留现有语义，并增加发布失败专用退出码。

爬虫过程中不调用 LLM；发布过程中不需要 LLM。

## 16. 明确禁止

1. 禁止让 App 直接访问本地爬虫电脑；
2. 禁止服务器在线运行爬虫才能响应用户；
3. 禁止把 SQLite 直接暴露给 App；
4. 禁止每次更新覆盖同一路径的所有封面；
5. 禁止把全量影视和封面长期提交进 Git 历史；
6. 禁止让 Worker 代理所有对象请求；
7. 禁止 App 用纯 `Promise.any` 接受最快但可能过期的 Manifest；
8. 禁止上传未通过数据质量门禁的局部结果；
9. 禁止在所有对象成功前更新 `current.json`；
10. 禁止把客户端加密宣传为真正保密；
11. 禁止把来源站结构直接暴露为 App 协议；
12. 禁止新增来源时复制整套爬虫、Feed 和发布流程。

## 17. 最终裁决

**推荐方案：R2 主数据面 + 阿里云国内镜像 + 现有六端点小型签名控制面。**

现有加密源的多端点经验应复用，但只复用于：

- 当前版本指针；
- Manifest；
- App 版本门控；
- 灾备。

影视大文件必须使用：

- 内容寻址；
- 不可变发布；
- 列表/详情/资源/封面分层；
- 哈希增量同步；
- 原子指针切换；
- 数字签名；
- 缓存优先和离线回退。

该架构在当前数据规模下可以接近零服务器计算成本运行，也为未来扩展到更多来源、更多影视、排行榜、评分回写和数万日活保留了清晰边界。
