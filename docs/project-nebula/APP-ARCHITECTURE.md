# magnetgoogo App 整体架构设计

文档版本：v0.1
更新时间：2026-04-25
适用范围：`magnetgoogo` 移动端 / 桌面端产品架构、客户端能力规划、商业化预留

> 说明：本文档聚焦“用户使用时极致顺畅好用”的 App 架构设计，强调信息极简、交互低负担、链路高确定性。本文档与 `docs/project-nebula/ARCHITECTURE.md` 的规则生产侧架构互补：前者回答“App 应该怎样组织，才能极致好用且可商业化”，后者回答“规则与供给侧如何生产与分发”。

## 1. 产品目标

`magnetgoogo` 的唯一核心目标是：

- 让用户最快发起搜索
- 让用户最快判断哪个结果最值得点击
- 让用户最快拿到磁力

App 不做资源站，不做论坛，不做内容社区，不让用户理解复杂来源结构。系统负责把复杂性隐藏在内部，只向用户暴露完成决策所需的最少信息。

产品关键词：

- 极简
- 快
- 稳
- 安静
- 可信
- 高级感

## 2. 设计原则

### 2.1 用户体验原则

- 首页只服务搜索，不承载运营噪音。
- 搜索结果只展示必要信息，不展示源站、规则细节、技术术语。
- 所有页面都优先缩短“搜索 -> 判断 -> 复制磁力”的路径。
- 首屏必须快，结果必须渐进式返回，不能让用户长时间等待空白页。
- 用户不需要学习产品，打开即可使用。

### 2.2 架构原则

- 体验优先于技术暴露：内部复杂度再高，也不能污染前台界面。
- 模块解耦：搜索、结果聚合、广告、会员、更新、风控必须可独立演进。
- 首版克制：首版聚焦极致搜索体验，推送与账号只做架构预留，不进入开发主线。
- 商业化前置设计：广告、会员、反破解、风控在架构层预留，避免后续重构主链路。
- 默认可观测：关键用户路径、广告触发、会员权益、反篡改状态都应有埋点与审计。

## 3. 产品范围

### 3.1 第一版必须实现

- 启动页
- 首页（未搜索态）
- 搜索结果页
- 历史搜索
- 收藏夹
- 关于页
- 基础设置页
- 广告插入框架
- 会员体系占位与免广告权益入口
- 强更能力
- 基础风控与反篡改框架

### 3.2 第一版明确不开发，但必须预留

- 推送更新内容触达
- 用户账户体系
- 云端同步
- 多设备会员同步
- 个性化推荐
- 反馈社区

### 3.3 第一版不做的原因

- 推送和账号都会显著增加服务端、隐私合规和状态管理复杂度。
- 首版目标是把“磁力搜索体验”打磨到足够强，而不是把产品做重。
- 先把核心搜索价值跑通，再决定哪些能力值得云化。

## 4. 信息架构

App 建议采用 4 个一级导航或 4 个主入口容器：

1. 搜索
2. 收藏
3. 历史
4. 我的

说明：

- `搜索` 是默认首页，也是产品绝对核心。
- `收藏` 承接用户复访价值，减少重复搜索。
- `历史` 承接高频找回场景，降低输入成本。
- `我的` 集中放置会员、设置、关于、版本信息、免责声明、广告说明等低频能力。

## 5. 页面级架构

### 5.1 启动页

目标：

- 极快进入可搜索状态
- 完成必要的配置拉取与环境检查

职责：

- 展示品牌与极简启动动画
- 加载本地缓存的配置、规则版本、会员状态快照
- 检查是否需要强更
- 检查本地反篡改状态
- 检查广告配置是否可用

约束：

- 启动页停留时间应尽量短
- 禁止在启动页堆提示、堆公告、堆营销

### 5.2 首页（未搜索态）

目标：

- 让用户零认知负担进入搜索

结构：

- 品牌名 `magnetgoogo`
- 大搜索框
- 一个主按钮 `搜索磁力`
- 轻量提示文案
- 最近搜索的极简入口

首页不应出现：

- 多级分类导航
- 源站列表
- 大量推荐内容
- 广告横幅
- 技术说明

### 5.3 搜索结果页

目标：

- 让用户在 1 到 2 秒内完成结果判断

结果页核心模块：

- 固定顶部搜索栏
- 结果排序条
- 轻量筛选栏
- 结果卡片流
- 渐进加载与骨架屏

结果卡片只保留必要信息：

- 文件名
- 类型
- 大小
- 文件数
- 高价值标签
- 系统质量判断信息
- `复制磁力`
- `立即打开`

不在结果卡片暴露：

- 磁力源
- 站点域名
- 抓取规则
- 健康灯状态
- 技术错误信息

### 5.4 收藏页

目标：

- 保存用户认为值得回看的结果

建议字段：

- 文件名
- 保存时间
- 标签
- 最近一次可复制时间

约束：

- 首版默认本地存储
- 不依赖账号

### 5.5 历史页

目标：

- 降低重复输入成本

建议内容：

- 最近搜索词
- 最近点击结果
- 最近复制的资源

能力：

- 一键重新搜索
- 批量删除历史
- 历史记录开关

### 5.6 我的页

用于承载低频但必要的系统能力：

- 会员中心
- 去广告说明
- 设置
- 关于
- 版本信息
- 隐私与免责声明
- 联系与反馈占位

### 5.7 关于页

关于页应做到轻量、清晰、可信，建议包含：

- 产品名称与版本号
- 产品定位说明
- 当前版本能力范围
- 联系方式或反馈入口
- 隐私政策与免责声明入口
- 开源声明或第三方组件说明

## 6. 核心用户链路

### 6.1 主链路

```text
启动 -> 首页输入关键词 -> 搜索 -> 渐进返回结果 -> 用户判断 -> 复制磁力 / 立即打开 -> 返回继续搜索
```

这是整个产品最重要的链路，任何能力都不能破坏它。

### 6.2 次链路

- 搜索 -> 收藏
- 搜索 -> 历史回找
- 触发广告 -> 关闭广告 -> 回到结果
- 免费用户达到门槛 -> 展示会员免广告引导 -> 继续使用

### 6.3 非核心链路

- 查看关于
- 查看版本
- 修改设置
- 联系反馈

这些链路必须存在，但不能抢占主链路。

## 7. 客户端分层架构

建议客户端分为 6 层：

1. 展示层
2. 交互编排层
3. 领域能力层
4. 商业化层
5. 系统安全层
6. 基础设施层

### 7.1 展示层

负责所有页面、卡片、骨架屏、弹层、广告位容器和会员引导 UI。

要求：

- 不直接依赖底层搜索实现
- 不直接感知规则与源站结构
- 通过 ViewModel 渲染稳定字段

### 7.2 交互编排层

负责页面状态流转和用户链路控制，例如：

- 搜索提交
- 搜索取消
- 搜索结果渐进合并
- 广告展示时机控制
- 会员弹层触发
- 强更拦截

### 7.3 领域能力层

这是 App 的业务核心，建议拆为：

- SearchDomain：搜索、排序、筛选、结果去重
- ResultDomain：结果标准化、标签归一、卡片映射
- HistoryDomain：搜索历史、点击历史、复制历史
- FavoriteDomain：收藏管理
- MembershipDomain：会员状态与权益映射
- AdDomain：广告频控、广告收益位管理
- AboutDomain：版本说明、政策文案、帮助信息

### 7.4 商业化层

负责：

- 广告联盟接入适配
- 广告策略编排
- 会员免广告判断
- 付费墙触发逻辑
- 收益统计埋点

### 7.5 系统安全层

负责：

- 反篡改
- 反调试
- 关键配置校验
- 本地配置签名校验
- 环境风险感知

### 7.6 基础设施层

包括：

- 本地缓存
- 网络请求
- 配置中心
- 埋点与日志
- 崩溃捕获
- 远程开关

## 8. 搜索体验架构

### 8.1 搜索输入

应支持：

- 关键词搜索
- 年份 / 清晰度 / 字幕等自然混合输入
- 历史词快速回填

不应支持：

- 复杂查询语法教育
- 高学习成本的高级检索入口

### 8.2 搜索执行

搜索执行应遵循：

- 秒级响应搜索态切换
- 有缓存时优先用缓存回显
- 结果渐进式返回
- 去重后稳定插入
- 默认相关性排序

### 8.3 搜索反馈

应提供：

- 骨架屏
- 搜索中状态
- 空结果提示
- 弱网降级提示

不应提供：

- 技术失败栈
- 源站失败明细
- 让用户理解内部抓取过程的提示

## 9. 数据与状态架构

### 9.1 本地数据域

首版应全部支持本地化独立运行，至少包括：

- 搜索历史
- 收藏数据
- 最近结果缓存
- 配置缓存
- 广告展示计数
- 会员状态快照
- 强更配置快照

### 9.2 远端配置域

建议使用远程配置中心管理以下内容：

- 强更开关
- 广告开关
- 广告频次阈值
- 广告联盟优先级
- 会员引导文案
- 实验分流开关
- 风险拦截开关

### 9.3 状态同步原则

- 没有账号时，所有状态默认本地优先
- 远程配置只覆盖产品策略，不覆盖用户个人数据
- 配置拉取失败时要有本地兜底

## 10. 商业化架构

商业化必须遵守一个原则：

- 不能毁掉主搜索体验

### 10.1 免费版与会员版

免费版：

- 正常搜索
- 正常复制磁力
- 有广告
- 有广告展示频控

会员版：

- 免广告
- 更纯净的搜索体验
- 可预留更快搜索 / 更高频使用等后续权益

### 10.2 广告架构

广告不应该常驻首页主视区，建议采用以下结构：

- 结果页信息流广告
- 页面切换间隙广告
- 达到使用阈值后的激励式或插页式广告

首版建议支持的广告位抽象：

- `search_result_inline_ad`
- `session_interstitial_ad`
- `usage_threshold_reward_ad`

### 10.3 广告触发策略

建议按“浏览一定页面后再看广告”设计，避免首次使用即打断：

- 用户首次进入不弹广告
- 搜索若干次后触发一次轻插页
- 连续浏览若干页结果后触发一次广告
- 复制磁力前不要强插广告
- 搜索中不要弹广告

推荐控制原则：

- 广告绝不打断输入
- 广告绝不打断首屏结果判断
- 广告触发必须可频控
- 广告触发必须能被会员权益关闭

### 10.4 广告联盟接入

商业化层应设计成适配器模式，便于后续接入多个广告联盟：

- AdMob
- 穿山甲
- 优量汇
- 其他第三方广告联盟

统一抽象接口应覆盖：

- 广告加载
- 广告展示
- 展示成功回调
- 点击回调
- 失败回调
- 收益归因回调

### 10.5 会员免广告能力

会员系统即使首版不做完整账户，也应先设计权益层：

- 本地会员态占位
- 会员权益枚举
- 免广告判定入口
- 购买成功后即时刷新广告层

建议会员权益先只做一项核心权益：

- `remove_ads`

这样产品逻辑最清晰，也最容易让用户理解。

## 11. 防破解与安全架构

说明：本节仅描述产品与架构层的防护思路，不展开对抗性细节实现。

### 11.1 防破解目标

- 防止广告逻辑被轻易跳过
- 防止会员状态被本地简单篡改
- 防止关键远程配置被伪造
- 防止 App 被明显二改后继续直接分发

### 11.2 防护层次

建议采用分层防护：

1. 本地完整性校验
2. 配置签名校验
3. 核心权益判定多点校验
4. 运行环境风险识别
5. 服务端策略联动预留

### 11.3 架构要求

- 会员状态不能只依赖单点本地布尔值
- 广告关闭状态不能只靠前端开关
- 强更配置与关键商业化配置需要签名或校验机制
- 高风险环境下可降级部分商业化能力或限制敏感入口

### 11.4 风险处理原则

- 优先静默记录与上报
- 必要时降级能力
- 避免无意义误伤正常用户
- 安全策略不能拖慢核心搜索路径

## 12. 用户账户架构预留

第一版不开发账户，但要预留以下边界：

- `AccountDomain`
- `IdentityProviderAdapter`
- `CloudSyncAdapter`
- `MembershipSyncAdapter`

未来接入账号后建议支持：

- Apple / Google / 手机号登录
- 收藏同步
- 历史同步
- 会员状态同步
- 换机恢复

首版因为无账户，必须明确：

- 会员逻辑先做本地占位或本地购买态闭环
- 收藏与历史均为本地数据

## 13. 推送能力架构预留

第一版不开发推送，但架构上要预留：

- PushDomain
- PushPermissionManager
- PushTemplateCenter
- DeepLinkRouter

未来可用场景：

- 新版本更新提醒
- 会员权益提醒
- 活动与运营通知

推送必须坚持：

- 默认克制
- 不骚扰
- 不破坏高级感

## 14. 更新与版本治理

### 14.1 强更

App 首版就应具备强更能力，原因：

- 搜索类产品依赖规则与策略，版本兼容性很重要
- 商业化与安全策略可能需要快速收口

强更链路建议：

- 启动时检查版本配置
- 若命中强更，则阻断主流程并引导更新
- 强更页文案简洁明确，不做复杂解释

### 14.2 普通更新

普通更新可通过：

- 关于页展示版本号
- 设置页提示新版本
- 后续再接推送提醒

## 15. 埋点与可观测性

建议埋点围绕 4 类指标：

### 15.1 核心体验指标

- 启动耗时
- 首页到首个结果耗时
- 首屏结果点击率
- 复制磁力成功率
- 搜索结果为空率

### 15.2 商业化指标

- 广告展示次数
- 广告填充率
- 广告点击率
- 会员转化率
- 会员免广告命中率

### 15.3 稳定性指标

- 崩溃率
- 配置拉取失败率
- 搜索失败率
- 强更命中率

### 15.4 风控指标

- 完整性校验失败次数
- 可疑环境命中率
- 会员状态异常率
- 广告策略绕过异常率

- 收藏
- 历史
- 关于
- 设置

### Phase 2：商业化闭环

- 广告联盟接入
- 广告频控

### Phase 3：账号与同步

## 17. 首版关键取舍

首版最重要的不是功能多，而是下面这些事情必须做好：

- 搜索框体验极顺
- 搜索结果卡片极易判断
- 复制磁力极快
- 广告不过度打扰
- 页面层级极浅
- 设置与关于足够克制

如果某项能力会增加复杂度但不能显著提升主链路体验，应延后开发。

## 18. 结论

`magnetgoogo` 的架构不应该像一个功能堆叠 App，而应该像一个围绕“搜索 -> 判断 -> 获取”打磨到极致的单核心产品。

因此：

- 前台必须极简
- 后台必须模块化
- 商业化必须可插拔
- 安全必须前置预留
- 非核心能力必须延后

只有这样，才能既保证第一版极致顺畅，又为后续广告、会员、账户、推送和风控留下足够稳的演进空间。
