## 2. 重新审阅发现的问题

### 2.1 全局limit无法保证两类各100条

旧聚合器只有一个全局`limit`。某类更新时间更近时会挤占另一类，无法证明最终是电影100+电视剧100。

修复：增加`movie_limit / series_limit / strict_kind_limits`，并分别导出电影和电视剧目录。严格模式任一类型不足即失败，不写伪完整结果。

### 2.2 同一磁力可能因标题或标签不同重复

旧逻辑按完整资源JSON去重。同一`info_hash`若展示标题或质量标签不同，会保留多份。

修复：磁力优先按`info_hash`，其他资源按类型+提供方+URL去重，并合并质量标签和缺失字段。

### 2.3 缺季数记录存在传递桥接风险

未知季记录可能通过标题连接第一季，又通过IMDb连接第二季，普通并查集会把两季误合并。

修复：两阶段归并。先只合并明确季/年份；未知分量只有在所有别名都解析到唯一明确候选时才并入，冲突则保持独立。

### 2.4 pending被错误返回为不可恢复失败

长任务每批结束后的正常状态是`pending`，旧CLI返回码1，与部署说明中的“退出码2可恢复”不一致。

修复：`pending`和`partial`统一返回2。

### 2.5 大快照镜像故障切换预算不足

SixV电影100条需要4个列表请求，旧快照总预算也是4；主站失败一次后，备用镜像无法完成完整列表。

修复：SixV快照预算提升到12，DYTT提升到6，并增加“主站失败1次+镜像完整4页”的100条永久反例。

### 2.6 本地预算耗尽被误判为站点限流

批次条目数与物理预算相等，任一网络重试会耗尽预算。旧错误码仍是`LIVE_RATE_LIMITED`，会误触发站点硬暂停。

修复：新增`LIVE_REQUEST_BUDGET_EXHAUSTED`；本地预算耗尽停止当前批次但保持可恢复，不触发403/429退避。默认每批5条预留12次物理请求。

### 2.7 冻结快照验证不足

旧门禁只检查URL唯一，未验证稳定内容键唯一、键与详情路径一致、内容类型和品牌契约。

修复：增加稳定路径、唯一键、非空标题、content_kind和brand_id验证；加载已有快照时重复验证。

### 2.8 发现历史0007迁移版本碰撞

历史SixV正式库的0007 checksum对应早期IMDb评分字段，而品牌分支也使用0007。库记录为0007，但没有品牌/季集字段。

修复：

- 生产迁移必须连续且版本唯一；
- 精确识别历史checksum；
- 仅当`imdb_rating/imdb_rating_text`完整，且品牌字段/索引完全未应用时，归档为`0007_legacy_imdb_rating_9316572e`；
- 随后执行正式0007品牌迁移；
- 任何部分结构或伪造checksum继续失败。

正式库迁移前使用SQLite backup API生成备份。
