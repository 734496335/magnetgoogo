# 导航站发现、导航解析与磁力源验证策略

更新时间：2026-04-21
适用范围：Project Nebula 供给侧 / `sources.json` 规则生产线

> **历史经验文档，非当前状态/测试 authority。** 当前执行使用 `SOURCE-CRAWL-AND-TEST-PLAYBOOK.md`；当前 `sources.json` 只允许 `green|yellow|gray`，本文历史 `red` 概念不得写入生产 contract；GREEN 必须满足当前双 bait 差异化 magnet 证据。

## 1. 目标

本策略文档用于沉淀当前在中国大陆可达环境下，针对磁力站导航页、导航站内部跳转页、候选磁力源本体所采用的实际工作流。

目标不是“一次性自动找全”，而是通过分层验证，把候选源稳定地收敛到以下几类：

- `green`：已经验证可搜索到磁力链或可稳定提取 hash
- `yellow`：页面仍显示明显磁力相关内容，但自动化暂时无法稳定提取，需人工/半人工确认
- `red`：确认已失效、已变导航站、已转非磁力内容、域名停放或空页
- `gray`：当前环境无法判断（例如网络不可达）

---

## 2. 总体原则

### 2.1 先广后深

按以下顺序推进，而不是直接对全部候选做重型浏览器验证：

1. 找导航站 / 聚合站
2. 从导航站提取“疑似磁力源”条目
3. 解析导航站跳转页，拿到真实外链域名
4. 对真实域名做 HTTP 级快速验证
5. 对 HTTP 无法确认但页面明显相关的源做浏览器级验证
6. 仍无法自动确认但页面明显有磁力关键词的，保留为 `yellow`

### 2.2 不误杀优先于过度清理

对于如下情况，不直接标红：

- 页面有明显磁力/种子/BT 关键词
- 站点像是 JS 渲染搜索页
- 搜索结果可能在详情页中，搜索页本身不直接给 magnet
- 存在跳转、镜像、Cloudflare、人机验证、按钮触发等情况

只有在“确认已失效/无关/空白/停放/非搜索站”时才标记为 `red`。

### 2.3 实际判定优先于名字猜测

品牌名、导航站文案、标题文本只能作为线索，不能直接当作可用证据。

最终是否升级为 `green`，以“能提取到磁力链、hash，或至少在详情页 URL 中稳定提取 40 位 hash”为准。

## 3. 找导航站策略

### 3.1 来源类型

当前已实践过的导航站发现来源主要有：

1. 搜索引擎结果页
   - 关键词：`磁力搜索`、`BT导航`、`种子搜索`、`磁力网站导航`、品牌名 + `官网` / `最新地址`
2. 已知导航站反向扩散
   - 从一个导航站继续找它链接出去的其他导航站
3. 旧品牌复活链路
   - 通过品牌名找到“发布页 / 导航页 / 聚合页”，再继续往真实源追
4. 已有候选源的友情链接/推荐列表
   - 某些磁力站自身也会挂“推荐站点”“镜像站点”

### 3.2 导航站识别特征

符合以下特征的页面，优先归为“导航站/目录站”：

- 一个页面列出大量站点卡片/站点清单
- 文案以“推荐站点”“最新地址”“网址大全”“聚合导航”为主
- 单页存在几十个站点入口，且入口文本是品牌名而不是资源标题
- 页面本身没有实际资源搜索结果列表
- 点击条目进入的是中转详情页，而不是直接资源搜索结果

### 3.3 当前有效经验

在本项目中，导航站爬取是发现候选域名的最高产策略之一，但它的产出默认不是最终可用源，而是“候选入口集合”。

也就是说：

- 导航站适合做 `candidate discovery`
- 不适合直接当作 `green source`

## 4. 解析导航站策略

### 4.1 两层解析模型

对导航站的解析分为两层：

#### 第一层：提取导航条目

从导航站首页/分类页中提取：

- 站点名称
- 分类
- 内部详情页 URL
- 描述文案

例如 `btmayi.top` 的“磁力搜索”分类中，提取到的很多链接并不是外部真实域名，而是它站内的详情页，如：

- `btmayi.top/cilisousuo/xxx.html`

#### 第二层：从详情页还原真实外链

导航站详情页常见模式：

- 页面中直接放外链按钮
- `go/?url=` / `jump?url=` / `redirect?url=` 中转链接
- `url=` 参数里包了明文 URL
- `url=` 参数里包了 base64 编码内容
- JS 中写 `window.location = ...`
- `meta refresh` 自动跳转
- `data-url` / `data-href` 属性中保存真实地址

因此解析详情页时，需要按优先级做多通道提取，而不是只看 `<a href>`。

### 4.2 当前已验证有效的提取顺序

当前实际采用的外链提取顺序为：

1. 直接外部链接（非本站域名）
2. `go.php` / `go/` / `redirect` / `jump` 等中转链接
3. `url=` 参数中的真实链接
4. `url=` 参数中的 base64 编码链接
5. `data-url` / `data-href`
6. `meta refresh`
7. JavaScript 中的 `location.href` / `window.location`
8. 页面正文中的“官网/地址/网址/链接”后跟 URL
9. 主内容区纯文本 URL

### 4.3 导航站解析的关键结论

对 `btmayi.top` 的实践表明：

- 导航站首页提取到的并不是真实磁力源域名
- 必须继续下钻到每个条目的内部详情页
- 很多详情页通过中转/编码方式隐藏真实目标站
- 真实目标站拿到后，还需要再做独立验证，不能直接入库为 green

## 5. 解析磁力源策略

拿到真实域名后，对磁力源本体采用分级验证。

### 5.1 第一级：HTTP 快速探测

目标：低成本快速判断是否值得继续深挖。

主要检查：

1. 主页可达性
   - DNS / 连接 / 超时 / HTTP 状态码
2. 页面大小
   - 极小页面常见于空壳、停放、错误页
3. 标题与正文关键词
   - `magnet`、`torrent`、`btih`、`磁力`、`种子`、`BT`
4. 停放/出售特征
   - `domain for sale`、`hugedomains`、`sedo`、`域名出售`
5. 搜索表单识别
   - form action / method / input name

如果主页完全无关、极小、停放、404，则优先判为 `red`。

### 5.2 第二级：多路径 HTTP 搜索

对仍像磁力站的源，尝试常见搜索路径模板，例如：

- `/search?q={query}`
- `/search/{query}`
- `/?q={query}`
- `/?s={query}`
- `/search?keyword={query}`
- `/search?query={query}`
- `/s/{query}`
- `/so/{query}.html`
- `/vodsearch/{query}/`
- `/list.html?key={query}`
- 以及从首页 form 中推断出来的 action + param

诱饵词以真实影视资源名优先，例如：

- `Inception`
- `Big Buck Bunny`
- `mp4`（兜底）

### 5.3 第三级：提取策略

搜索结果页或详情页中，优先按以下方式提取有效证据：

1. 直接 `magnet:?xturn:btih:` 链接
2. 链接中的 40 位十六进制 hash
3. 正文中的 40 位十六进制 hash
4. 详情页 URL 中可稳定识别的 hash

如果搜索结果不直接给 magnet，但详情页链接里包含稳定的 40 位 hash，也可视为“可工作搜索源”的强证据。

### 5.4 第四级：浏览器级验证

当 HTTP 层满足以下任一条件时，进入浏览器级验证：

- 首页有明显磁力关键词，但 HTTP 搜索提取不到结果
- 页面疑似前端渲染
- 搜索页结果需要点击/展开/进入详情页才出现 magnet
- 存在 Cloudflare / WAF / JS 延迟加载

已实践过的浏览器级方案：

- Selenium（早期）
- Playwright（后期，稳定性更好）
- 人机协作浏览器验证（人工处理验证码/Cloudflare，脚本负责提取）

## 6. 状态判定策略

### 6.1 升级为 green 的条件

满足以下任一条件即可：

1. 搜索结果页直接提取到 magnet 链接
2. 搜索结果页/详情页可稳定提取多个 40 位 hash
3. 结果列表明确展示资源标题，详情页 URL 中包含可稳定还原的 hash

### 6.2 保留为 yellow 的条件

满足以下条件时优先保留而非误杀：

- 页面仍有明显磁力相关关键词
- 浏览器渲染后仍能看到“像磁力站”的结构
- 搜索功能疑似存在，但自动化暂时无法稳定提取
- 需要人工点击、手动过验证、进入详情页后才能拿到磁力证据

当前 yellow 的实际含义是：

> “这个站点依然值得继续验证，但当前自动化管线证据不足，暂不误杀。”

### 6.3 降级为 red 的条件

满足以下任一条件即可：

- 域名停放 / 售卖页
- 404 / 空白页 / 极小页
- 已变成导航站、目录站、资讯站而非搜索引擎
- 页面完全没有磁力相关内容
- Playwright/HTTP 多轮验证后，确认内容与磁力搜索无关

### 6.4 gray 的使用场景

- 当前网络环境无法判断
- GFW / DNS / timeout 导致完全不可达
- 证据不足，不适合直接 red，也没有页面内容可保留为 yellow

## 7. 实际经验总结

### 7.1 导航站本身不是结果，真实域名才是结果

这是当前策略中最重要的经验。

从导航站抓到品牌名和内部详情页，只能算“线索”，不能算“可用源”。必须继续还原真实外链并独立验证。

### 7.2 大量磁力站并不直接暴露 magnet 链接

常见原因：

- 结果在详情页
- hash 只出现在 URL 或文本里
- 页面靠 JS 渲染
- 需要按钮点击或延迟加载

因此“只找 `<a href="magnet:">`”会漏掉大量真实可用源。

### 7.3 自动化能力不足不等于站点失效

这是本轮清理中反复验证过的结论。

很多 yellow 源并不是坏站，而是：

- 搜索路径非标准
- 需要浏览器渲染
- 需要详情页二跳
- 需要人工处理验证

因此 yellow 的存在是有价值的，它表示“自动化没跟上，不代表站死了”。

### 7.4 真正该 red 的，往往特征很明显

例如：

- 只有几十或几百字节
- 只有停车页文案
- 变成介绍页/资讯页/导航页
- Playwright 跑完依旧无任何磁力相关内容

这类源适合果断 red。

---

## 8. 当前建议工作流

后续继续扩展源时，建议严格按以下顺序：

1. 发现导航站 / 聚合站
2. 提取导航条目
3. 下钻详情页，解析真实外链域名
4. 去重并与 `sources.json` 交叉比对
5. 对新域名做 HTTP 快速探测
6. 对有关键词但未提取成功的源做浏览器级验证
7. 仅对明确成功者标 green
8. 仅对明确失效/无关者标 red
9. 其余保留 yellow，进入人工验证池

## 9. 与脚本的对应关系

当前策略对应的主要脚本：

- 导航站条目提取：`btmayi_sites.json` 相关提取链路
- 真实域名还原：`magnet/extract_btmayi_domains.py`
- 批量 HTTP 验证：`magnet/batch_verify.py`
- 人机协作验证：`magnet/human_verify.py`
- 中国大陆可达源发现：`magnet/discover_china_sources.py`
- 品牌到域名恢复：`magnet/brand_resolver.py`
- 浏览器级验证：`magnet/playwright_verify.py`

这些脚本不是互相替代关系，而是同一条生产链上的不同阶段。

## 10. 后续优化方向

1. 对 yellow 源做站点专属适配，而不是继续堆通用搜索路径
2. 在 Playwright 中增加详情页点击、按钮点击、hash URL 提取逻辑
3. 为导航站详情页建立更健壮的编码/中转解析器
4. 对“导航站 / 搜索站 / 资讯站 / 停放页”建立更稳定的页面分类器
5. 对 yellow 建立人工复核工作池，而不是继续全自动误判
