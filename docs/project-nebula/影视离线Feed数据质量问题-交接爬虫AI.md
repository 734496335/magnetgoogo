# 影视离线 Feed 数据质量问题——交接爬虫 AI

日期：2026-07-26
范围：`data/resource_index/sixv_app_bundle/feed.json`、`data/resource_index/series_latest_100_feed.json` 及其上游影视采集、解析、合并、导出流程
边界：本文只描述数据生产问题与验收标准；App 仅保留必要的展示兜底，不在本轮修改爬虫实现。

## P0-1：电视剧没有本地封面资产

### 现状证据

- 当前 100 条电视剧均有 `cover_source_url`。
- 当前 100 条电视剧均没有 `cover_asset_path`。
- App 只能临时使用远程封面并依赖系统缓存；离线、弱网或图片源失效时会退化为占位海报。

### 目标

数据生产侧在生成 Feed 时下载、校验并压缩电视剧封面，输出与电影一致的本地资产契约：

- `cover_asset_path`
- `cover_width`
- `cover_height`
- 内容哈希
- 本地文件真实存在

建议单张封面控制在约 30–80KB，优先 WebP/JPEG，最长边不超过 720px。App 运行时不应依赖资源站图片域名。

### 验收

- 100 条记录全部有安全相对路径。
- Feed 汇总满足 `cover_count == record_count == 100`。
- 构建后断网打开电视剧频道，列表和详情页均能显示真实封面。

## P0-2：资源标题丢失集数语义

### 现状证据

影片：`X战警97 第一季`
媒体 ID：`movie:9b2d76c3141ab99a5408f46a7bceb499ee6eb30c1082d9d86bc9a99f23cf6226`

Feed 中大量磁力资源的 `display_title` 都只是：

```text
1080P
```

但磁力 URL 的 `dn` 参数实际包含明确集数，例如：

```text
X-Men 97 S01E01 ... 1080p ...
X-Men 97 S01E04 ... 1080p ...
X-Men 97 S01E10 ... 1080p ...
```

因此集数信息在源数据里存在，是导出 `display_title` 时被丢弃，并非资源站没有提供。

### 目标

导出资源标题时按以下优先级取值：

1. 源站真实资源标题；
2. 磁力 `dn` 参数；
3. 文件名；
4. 最后才退化为清晰度标签。

建议输出：

```text
S01E01 · 1080P
S01E04 · 1080P
S01E10 · 1080P
```

建议新增资源级结构化字段：

- `season_number`
- `episode_start`
- `episode_end`
- `episode_label`

### 验收

- 当磁力 `dn` 中存在 `SxxExx`、`E01`、`第01集` 等模式时，`display_title` 不得只剩 `1080P/4K/HD`。
- 同一剧集中不同集数的标题必须可区分。
- 增加针对 `S01E01`、`S01E01-E02`、`第1-2集` 的自动测试。

## P0-3：第一季条目混入第二季资源

### 现状证据

`X战警97 第一季` 的资源集合中同时出现：

```text
S01E01
S01E10
S02E01
S02E03
S02E06
```

这说明当前合并身份只按系列名称聚合，未严格按季分桶，导致第一季详情页混入第二季资源。

### 目标

媒体身份至少包含：

```text
规范化系列名 + season_number
```

当资源可解析出季号时，必须与条目季号一致；无法判断季号的资源进入待审计集合，不得静默并入明确季条目。

### 验收

- `第一季` 条目不得包含 `S02Exx` 资源。
- 同一系列不同季应生成独立媒体条目或明确的季级资源分组。
- 增加“跨季资源不得错误合并”的反例测试。

## P0-4：电影类型与国家字段包含解析残片

### 现状证据

问题集中在电影 Feed：

```text
data/resource_index/sixv_app_bundle/feed.json
```

当前 50 部电影中检测到：

- 25 个异常类型值；
- 14 个异常国家地区值；
- 电视剧 Feed 当前没有命中同类异常，但必须共用同一数据质量门禁。

真实异常示例：

```text
: 喜剧
: 剧情
惊悚 片"> 惊悚
纪录 片
: 美国
: 中国 大陆
```

这说明详情页 HTML/文本解析后，没有在数据生产侧完成标签节点提取、HTML 残片剥离和规范化，导致展示层收到不可直接使用的分类值。

### 根因要求

不得只在 App 中修字符串。数据生产侧需要在解析和导出阶段统一完成：

1. 从正确的 DOM 节点或结构化字段提取类型、国家地区，不把标签周边 HTML 文本写入值；
2. 去除前导 `:`、`：`、分隔符和多余空白；
3. 清除 `<...>`、`">` 等 HTML 残片；
4. 统一同义和空白变体，例如 `纪录 片 -> 纪录片`；
5. 去重后再写入 `genres`、`countries`；
6. 原始值如需审计，应写入独立 `raw_*` 字段，不得污染面向 App 的规范字段。

建议数据侧提供统一函数：

```text
normalize_genre_label(raw)
normalize_country_label(raw)
```

该函数应在所有电影、电视剧来源的最终导出前强制执行，而不是只针对 SixV 打补丁。

### 验收

- `genres`、`countries` 中不得出现前导冒号、HTML 标签、`">`、异常尾部“ 片”或连续空白；
- 规范字段必须满足“单一纯文本分类值”，不得包含页面结构字符；
- `惊悚 片"> 惊悚` 必须归一为 `惊悚`；
- `纪录 片` 必须归一为 `纪录片`；
- `: 美国` 必须归一为 `美国`；
- `: 中国 大陆` 应按数据契约拆分或规范为可稳定匹配的国家地区值；
- 对电影和电视剧 Feed 同时运行质量门禁，异常数量必须为 0；
- 增加包含上述真实反例的自动测试，防止解析器升级后回归。


典型问题包括：

- 原始顺序为 `S01E04 / S01E03 / S01E01 / S01E02`，不能直接供 App 展示；
- 第一季条目混入第二、第三季资源；
- 19 部剧的标题季号与结构化 `season_number` 冲突，例如“第一季”却写入 `season_number=2`；
- 条目字段 `season_number` 与标题季数、资源季数互相冲突；
- `display_title` 只有 `1080P/720P`，集数只存在于 magnet `dn`；
- 17 部剧只有整季包或无法解析季集的资源，不能形成正常剧集序列；
- 同一集存在多个发布版本时，只提供相同的“集数 + 清晰度”，没有编码、来源、发布组、大小等可区分信息。

### 根因要求

数据生产侧必须在最终聚合和导出前建立资源级标准结构：

```text
season_number
episode_start
episode_end
episode_label
resource_scope        # episode / episode_range / season_pack / series_pack / unknown
release_group
video_source          # WEB-DL / WEBRip / BluRay 等
video_codec           # H264 / H265 / AV1 等
resolution
file_size_bytes
variant_label
```

处理顺序必须为：

1. 从源站资源标题提取季集；
2. 源站标题不足时解析 magnet `dn`；
3. 再尝试真实文件名；
4. 按媒体条目的季号校验资源归属；
5. 跨季资源必须拆分到对应季，不能静默混入；
6. 对同季资源按 `season_number / episode_start / episode_end / 版本质量` 生成稳定顺序；
7. 无法确认季集的资源进入 `unknown` 审计集合，不得伪造成普通单集；
8. 最终 `display_title` 必须让用户直接看出集数或“整季包”，不得只剩清晰度。

### 验收

- `S01E01 < S01E02 < S01E03 < S02E01`；
- `items_out_of_source_order == 0`；
- `items_with_title_field_season_conflict == 0`；
- 明确季条目的 `cross_season_resource_count == 0`；
- magnet `dn` 可识别集数时，`display_title` 不得只显示 `1080P/720P/4K`；
- `unknown_identity_count` 必须有明确原因和待审计输出，不能静默丢失；
- 同一集多个资源必须通过 `variant_label` 或版本字段可区分；
- 增加真实反例测试：X战警97、犯罪心理、末日地堡、谜探休格、瑞克和莫蒂；
- 数据侧修复后重新运行 `npm run audit:series-resources`，并将结果绑定到 Feed 生成提交。

## P1-2：缺少真实排行榜或热度依据

### 现状证据

现有 Feed 只有抓取顺序、更新时间、更新状态、评分、地区和资源数量，没有播放量、站内热度或权威榜单排名。

### 产品约束

App 当前只展示“追更速递”和“最近更新”，不会把抓取顺序伪装成排行榜。

### 后续建议

如要增加“排行榜”，数据侧必须提供至少一种可审计依据：

- 来源站真实榜单名和排名；
- 多来源共同出现次数；
- 豆瓣/IMDb 评分与有效评分人数；
- 明确的热度计算公式与生成时间。

字段建议：

```text
ranking_type
ranking_name
ranking_position
ranking_score
ranking_evidence
ranking_generated_at
```

没有证据时不得输出“热播榜第 N 名”等误导性文案。

## App 临时兼容措施

在数据侧修复前，App 已采取以下临时措施：

1. `cover_asset_path` 缺失时使用 `cover_source_url` 并启用图片缓存；加载失败仍有本地占位海报。
2. 当资源标题只有 `1080P/4K/HD` 时，从磁力 `dn` 中提取 `SxxExx` 或中文集数，显示为 `S01E01 · 1080P`。
3. App 只做展示层补救，无法可靠修正跨季资源混入；跨季归属必须由数据生产侧修复。
4. App 临时清理类型和国家字段中的前导冒号、HTML 尾片及空白变体，并合并同义分类，避免脏数据直接污染频道和类型胶囊。
5. 上述展示清洗不是验收终点；数据侧修复后，Feed 原始规范字段本身必须通过 P0-4 的零异常门禁。
6. App 会按解析出的季号、集号自然排序，并将整季包和无法识别季集的资源放在单集资源之后。
7. App 详情页会从 magnet `dn` 恢复可证明的集数标题，但不会自行改写跨季归属或伪造未知集数。
8. App 对同集多版本只展示现有质量标签；版本级可区分字段仍必须由数据侧按 P0-5 补齐。
